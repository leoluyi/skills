# 文件骨架模板

兩種定位共用同一套段落積木，差別在取捨與口吻。先看共用積木的寫法示範，再看兩種模式的組裝順序。

## What/Why 論述的寫法

三段各自要回答的問題，與好壞對照：

**功能定位** — 回答「它站在系統的哪裡」。

> 不合格：Istio 是一個 service mesh。
>
> 合格：Istio 在微服務架構裡佔的位置是「服務與服務之間的通訊層」：它把原本散落在各服務程式碼裡的流量控制、加密、觀測邏輯，抽出來放進與應用程式並行的 sidecar proxy（或 ambient 模式的節點層代理），讓應用程式碼回到只處理商業邏輯。

**解決的問題** — 回答「沒有它，大家原本怎麼受苦」。這段是整份文件的錨點，寫的時候想像讀者會問「所以呢？我為什麼要在乎？」。

> 不合格：它解決了微服務通訊的問題。
>
> 合格：服務數量到幾十個之後，每個團隊各自在程式碼裡實作 retry、timeout、mTLS，實作品質不一且無法統一稽核；金融業的資安檢視會直接卡在「你如何證明所有服務間流量都加密」這一題。Service mesh 把這些橫切關注點下沉到平台層，讓「全部加密」從各團隊的自律變成平台的預設。

**主要功能要求** — 回答「它做到什麼才算稱職」，用可檢驗的敘述。

> 不合格：提供流量管理、安全性、可觀測性。
>
> 合格：它至少要做到三件事才值得引入：(1) 服務間流量可以不改應用程式碼就套用路由規則與故障注入；(2) mTLS 可以全網格強制開啟並集中輪替憑證；(3) 每個服務之間的轉發延遲與錯誤率，可以在不修改應用程式碼的前提下被收集。

## 辯證比較五件套的寫法

以「service mesh vs API gateway」為例示範每段的責任：

1. **定義** — 各一句話。「API gateway 處理南北向流量（外部進入系統），service mesh 處理東西向流量（服務彼此之間）。」
2. **行為職責邊界** — 各自明確不管什麼。「Gateway 不知道也不介入服務 A 呼叫服務 B；mesh 不做對外的認證授權與 rate limiting，那是 gateway 的門面職責。」邊界寫清楚，後面的比較才不會變成雞同鴨講。
3. **比較分析** — 逐面向，且寫出差異的成因。「Gateway 是集中式單點，升級影響面大但運維心智負擔小；mesh 是分散式，proxy 隨服務部署，升級要處理資料平面滾動更新。」
4. **邊界判斷表** — 收灰色地帶：

   | 情境 | 用哪個 | 為什麼 |
   |---|---|---|
   | 對外 API 需要 API key 管理與計費 | gateway | 商業層關注點，mesh 沒有這個抽象 |
   | 內部服務間要 mTLS 與細粒度授權 | mesh | 東西向流量，gateway 看不到 |
   | 只有 5 個服務、單一團隊 | 都先不用 | 引入成本高於收益，函式庫級的 retry／timeout 就夠 |

5. **決策框架** — 「該採用」與「不該採用」各自寫成條件式：「服務數量超過 N、跨多團隊、有稽核要求 → 評估導入」「服務少、單團隊、無合規壓力 → 不要導入，運維成本會吃掉你」。

## 學習筆記模式的組裝順序（一頁筆記型）

```markdown
# <主題> — 一頁自學筆記

> **一句話：** <一句話定義，講清楚它把什麼問題交給誰處理>
> *<文件範圍行：定義 · 運作 · 邊界 · 決策> — 更新至 YYYY-MM*

## 為什麼會有它？            ← 解決的問題（What/Why 的錨點段）
## 它怎麼運作？              ← 功能定位 + 主要元件，配架構 Mermaid 圖或平面對照表
## <關鍵機制>白話版          ← 概念三拍：一句話／為什麼重要／要注意的坑
## 前置知識地圖              ← 模組，視需要
## 心智模型                  ← 模組，視需要
## 邊界地圖 — 它管什麼、不管什麼 ← 職責邊界 +「需求→工具→是否本職」表
## 決策表 — 什麼時候該用／不該用 ← 「訊號→傾向用／不用」雙欄表 + 成本誠實面對
## 選型速覽                  ← 主題有多個實作方案時
## 常見誤解與陷阱             ← 模組
## 動手驗證                  ← 最小可運行範例，視需要
## 用自己的話講一遍           ← 費曼式自述檢核（opt-in，使用者要求才放）
## 待驗證問題清單             ← 模組（opt-in；素材含使用者標記的未解問題時例外照收）
## 延伸參考                  ← 鄰近主題：定位、一句話對比、時效近況
## 一段話總結                  ← 三行收束：定義、強弱項、決策法則
## 參考來源
```

辯證比較五件套在這個骨架裡的落位：定義與職責邊界進「邊界地圖」，比較分析與邊界判斷表進「邊界地圖」＋「選型速覽」，決策框架進「決策表」。五件套是檢查清單，段落名稱跟著內容走。

## 正式文件模式的組裝順序

```markdown
# <主題>技術說明

> 本文內容確認至 YYYY-MM。適用版本：<如有>

## 概述                      ← 功能定位 + 解決的問題，濃縮版
## 前置知識                  ← 模組，視讀者而定
## <元件一>                  ← What/Why 論述，逐元件
## <元件二>
## 與<替代方案>的比較與選型     ← 辯證比較五件套
## 常見誤解與陷阱
## 驗證步驟                  ← 最小可運行範例，視需要
## 參考來源
```

正式模式下一律不含費曼檢核與待驗證清單；文中不留第一人稱與未查證的猜測。

## 混合模式

正文照正式模式寫；使用者有要求學習鷹架（費曼檢核、待驗證清單）時，收進文末「附錄：學習鷹架」一節，正本可直接刪附錄拿去給團隊看。沒要求就不加附錄。

## 情境模組的掛法

- **ADR** — 插在辯證比較之後，因為 ADR 的「考量的選項」直接引用比較分析的結論，不重寫一遍。
- **分層結構** — 取代「逐元件」的平鋪順序，成為文件中段的外框；每層底下仍是 What/Why 論述。
