# Mode D 既有文件改寫 — 判斷細節與改寫說明格式

## 先辨識文件出身

改寫深度由文件出身決定，不由使用者用哪個動詞決定。動筆前先判成兩類：

**已是本 skill 骨架 → 定點修補。** 判斷訊號兩類皆算：(a) v2.0.0 四型結構——文件已切成清楚分離的 tutorial／how-to／reference／explanation 區塊；(b) v2.0.0 之前的單一骨架——已有 What/Why 三段論述、辯證比較五件套、開頭一句話 blockquote、標了 as-of。兩者結構都是對的，工作集中在更新時效、補漏、併入新素材，不動已成立的論述。**意圖＝更新時效／併入新素材時，保留輸入原形（連 pre-v2.0.0 單一骨架也不強拆成四型），不跑 compass 重排。**

**外來格式 → 整份重構。** 判斷訊號：純功能羅列、沒有 What/Why、沒有比較替代方案的邊界、章節按官方文件的功能目錄排而非按「解決什麼問題」排。**AI 代筆稿是最難判的一種**：它行文流暢、讀起來像論述，卻沒有 What/Why 錨點與辯證五件套——流暢不等於有骨架，別被文氣騙成「已是骨架」。意圖＝重整／重構時，把素材交給 compass（SKILL.md S2）重新路由進四型區塊，等同對既有素材做一次原始資料整理（模式 B 的重組紀律），在改寫說明裡交代哪型新增、原內容各歸哪型。

判錯的代價不對稱：把外來格式誤判成骨架，會做出半套重構（掛了新標題但論述還是羅列）；把骨架誤判成外來格式，會把使用者已經寫對的論述整份推翻重寫。不確定就問使用者這份文件是不是先前用本 skill 寫的。

## 四種常見情境（可同時成立）

一次改寫常同時涵蓋數種；先辨識出身、問完保守／從零，再逐項處理。情境名已交代「做什麼」，下表只列各自的邊界——最容易越界或做半套之處：

| 情境 | 邊界（別越過的線） |
|---|---|
| 重構 | 原文章節結構可拆可改，別當成不可動的框 |
| 更新時效 | 逐一回一手來源重查，別採信舊文件寫的版本號直接沿用 |
| 併入新素材 | 只改被新素材影響的部分，別整份重產而丟掉新素材沒提、但既有文件本來寫對的內容 |
| 品質升級 | 只動結構層級；句子層級的 AI 味潤飾交給 avoid-ai-writing-zh，不在這裡代做 |

## 改寫說明格式（改寫任務一律附上）

```
## 改寫說明

**文件出身**：已是本 skill 骨架 → 定點修補 ／ 外來格式 → 整份重構（擇一）
**改寫姿態**：保守改寫 ／ 從零重產（使用者選定）

**結構變動**
- 新增：〈何時不該採用〉決策段
- 移除：原文重複的安裝步驟清單（併入最小可運行範例）

**時效性事實更正**（舊值 → 新值 ＋ 來源）
- OpenShift 4.14 → 4.16（官方 release notes，確認至 2026-07）
- 預設 runtime：runc → crun（Podman 5.x 官方文件）

**內容取捨**
- 保留：原文的 Ingress vs Gateway API 比較段（判斷仍成立）
- 併入：新版 release note 的 GAMMA 支援一節
- 覆蓋：原文「Gateway API 尚未 GA」的過時斷言
```
