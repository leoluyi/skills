## 樣本 3 — 條列式規劃文 A → id 70

```
1. AI微服務平台的目的是建置一座共用的 AI 微服務平台，將模型（LLM、向量檢索、多模態辨識等）封裝為標準化 API 服務，讓內部系統呼叫 AI 如同呼叫其他企業微服務，如統一介面、權限控管、稽核紀錄、用量追蹤等，集中管理下列問題:

   - 各團隊自行部署服務，其他系統難以共用、複用
   - GPU、Token、儲存等資源散落在各專案Silo，用量不可見也無法調控
   - 缺乏持續監控，品質劣化往往到使用者反映才察覺

2. 將多個獨立 AI 能力組合成完整業務流程編排複雜度應遵循漸進式原則:從最簡單的模式開始，只在前一層級無法滿足需求時才升級。高複雜度編排（尤其是自主式 Agent）會帶來顯著的 Token 消耗、延遲與稽核負擔。在金融業的延遲與合規敏感場景中，應優先以第一、二階解決需求。

   - 第一階:組合式模式 (Composable Patterns) — 大多數場景的預設選擇
   - 第二階:確定性流程 (DAG / State Machine) — 適用於步驟固定、需完整生命週期管理的業務流程 (如文件處理 pipeline)
   - 第三階:自主式 Agent (LLM-driven loop) — 僅適用於開放式、無法預先定義步驟的任務

3. 架構分層: 開放式元件優先以利技術迭代：優先採用有生產級別 (Production-Level) 的元件，避免 vendor lock-in

   - 平台應用：服務交付與系統介接、模型服務與管理、知識檢索、安全治理、營運與品質管理。
   - 中介軟體：API 閘道、映像倉庫、服務間通訊、訊息佇列。
   - 基礎設施：K8s 叢集、儲存、網路、GPU 資源調度。
   - 硬體平台：GPU / CPU / Storage / Network。

4. 知識移轉：除平台建置本身之外，需有知識移轉計畫，使本行團隊可培養研發能量，並能獨立維運。
```
