# Tech Writing — 技術描述的三種模式

本檔是**內容層**規範，與聲音層（voice-axes 的 preset）正交：任何 preset
都可以承載技術內容，但技術描述本身必須通過本檔的兩張檢查清單——
**可操作性**與**概念釐清**。技術文（教學、工具、框架、原理解說）必讀。

## 核心：三家的「描述基本單位」不同

| 模式 | 代表 | 基本單位 | 概念存在的目的 |
|---|---|---|---|
| 操作型 | 保哥 | 系統行為規則 | 讓操作可預測 |
| 概念型 | 高見龍 | 心智模型與定位 | 讓讀者能自己推理 |
| 推演型 | 倉鼠 | 讀者的認知階梯 | 讓讀者自己「發現」 |

三家都不寫純理論：**概念一律以「它決定了什麼行為」的形式出現**。
這是技術文與教科書的分水嶺。

## 模式一：操作型（保哥）——可重現優先

適用：教學文、設定手冊、工具導入、踩坑記錄。

**1. 心智模型先行，且以「系統行為規則」陳述。**
在任何步驟之前，先給讀者一組可預測系統的規則，必要時先糾錯
（「先導正觀念：別再把全螢幕當最大化！」）。規則寫成斷言：
「macOS 預設**不允許**一個視窗同時跨在兩個螢幕中間顯示。」
不是「macOS 的視窗哲學強調空間獨立性」這種摸不到的話。

**2. 操作以意圖為索引。**
每個操作的入口是讀者想達成什麼：「如果您只是想把視窗撐大，
但不希望它變成獨立的全螢幕空間，正確的操作是：」——
先 if（意圖），再 how（步驟）。讀者是帶著目的來的，不是來背功能表。

**3. 可重現四要素。** 每個操作寫齊：
- 前置條件（環境、版本、權限）
- 精確動作（「按住 `Option` 鍵，再點擊綠色按鈕」——鍵名、按鈕位置到位）
- 預期結果（「圖示會從雙向箭頭變成加號」——讀者能自我驗證有沒有做對）
- 副作用與善後（「修改設定後必須重啟 Dock 才能生效」）

**4. 指令規範。** 可複製、逐行註解寫 why、善後指令不省略。

**5. 術語精確是可操作性的一部分。**
術語錯了就搜不到文件、問 AI 問不準（保哥原話：連「好好說話」都沒辦法）。
複雜主題文末附術語對照表：正確中文｜正確英文｜常見誤稱｜觀念說明。

## 模式二：概念型（高見龍）——心智模型優先

適用：新概念導讀、工具選型、方法論介紹、易混淆概念梳理。

**1. TL;DR 先行。**
「怕內容太長大家沒耐心看完，基本上 OpenSpec 就三招：
proposal → apply → archive。」結論壓在最前面，讀者先拿到骨架再讀肉。

**2. 定義三段式：官方定義 → 白話翻譯 → 比喻回收。**
引 spec 原文 →「翻成白話文就是…」→ 劇情式比喻（小吃店收到台南小吃
完全手冊）→ 回收一句「Skills 就是這本秘笈」。

**3. 定位澄清（vs 混淆對象）。**
新概念必與讀者腦中最近的既有概念對比切割：Skills vs MCP ——
「一個是腦袋裡的知識，一個是手上的工具。」對比句式一句定生死。
讀者最需要的往往不是「它是什麼」而是「它跟我已知的 X 差在哪」。

**4. 演進脈絡定位。**
三階段敘事（一問一答 → Tool Calling → Skills）給新事物歷史座標，
讀者自然理解「它解決了上一階段的什麼問題」。

**5. 邊界與判斷標準（可操作性的高階形式）。**
不只教「怎麼用」，更教「什麼時候不用」：列不適用清單，每項附理由
（「修 bug 不需要走流程——修 bug 是讓程式符合規格，不是改變規格」），
最後收斂成一條**讀者可自行套用的判斷標準**：「判斷標準就是這次改動
會不會讓系統行為跟 specs 定義的不一樣。」教會判斷，勝過教十個步驟。

**6. 具體化模糊性。**
說「規格要精準」沒有用；用一顆按鈕連發七個問題示範什麼叫模糊
（modal 還是 modeless？在哪裡出現？怎麼關閉？按 ESC 會不會關？…）。

**7. 誠實面對缺點＋適用性免責。**
「講了這麼多好處，我們也要誠實面對它的問題」＋具體反例
（Kiro 生成 5,000 行、手動縮到 800 行）。結尾提醒
「選用工具有賺有賠，不要因為我說好用就跟著用」。

**8. 機制講 why。**
「雖然看起來只是在填表格，但其實是在強迫我們思考『這次變更會影響
什麼』。」讀者懂了機制的目的，就能推理未涵蓋的情況。

## 模式三：推演型（倉鼠）——認知階梯優先

適用：原理解說、抽象概念、深度解讀、翻譯改寫技術文。

**1. 範例先於機制。**
「進入技術細節之前，我想先用幾個範例提示詞，幫你想像可以做到什麼。」
先給 5–8 個具體用例撐開想像，再講運作原理。

**2. 逐步演示，讓讀者「發現」。**
教抽象概念用可跟隨的推演（格子遊戲一步步畫）：
「以此類推，最終會獲得：」→「好像沒看出什麼規則，那如果尺度拉大呢？」
→「竟然發現一件奇怪的事：**找不到固定的規律了**。」
結論由讀者跟著走到，不是被告知。

**3. 承重概念立樁。**
明確標記哪些概念是全文地基並要求讀者停留：「這兩個是貫串全文的
核心觀點，**一定要先知道這三行，後面才有辦法繼續讀**。」
之後每個新論點都回扣地基概念。

**4. 失敗模式具名化。**
抽象問題拆成有名字的 pattern，每個給定義＋具體例子：
Agentic laziness（50 項只處理 20 項就宣稱完成）、self-preferential
bias、goal drift。有名字才能被討論、被檢查。

**5. 術語三層法**（見 rewrite-playbook）＋原文沒有的白話成本註解。

## 教學／升級文的五個加值件

以下技巧操作型與概念型皆適用：

1. **讀者分流開場**：長教學／升級文在開頭按讀者意圖路由——
   「只想快速試新功能→這裡」「要從舊版升級→跳到第 X 節」。
   替不同目的的讀者各給一條最短路徑。
2. **Q&A 子結構**：每個功能／步驟講完，掛 2–3 題自問自答的
   「常見問題」，題目必須是使用中真會遇到的場景
   （「編輯到一半有緊急修改要上線怎麼辦？」），不是 FAQ 湊數。
3. **好奇支線**：安排一段「如果故意反著做會怎樣」的邊界實驗
   （「故意把它設成 false，會發生什麼事？」）——回答讀者不會問
   但會好奇的問題，順便劃清機制邊界。
4. **背景補課插播**：行文碰到關鍵依賴概念（如 Pyodide）時，
   停下來插 2–3 句科普＋一句誠實評價，再回主線。用「回到 X」
   收束插播。
5. **定性總評**：版本／工具評述的結尾給對象一個「性格」——
   「不算砍掉重練，比較像還技術債」。一句定性勝過條列重述。

**深度檔位對齊長度**：教學文的「導讀級」（只講重點與判斷）約對應
Step 1 長度檔位的「標準」；「工具書級」（每個選項、變數都解釋，
讀者不用再開第二篇）對應「工具書級」檔位。深度與長度連動：選了
工具書級長度就走窮盡式，選標準就走導讀式；寫升級指南、設定手冊
時若使用者沒定長度，主動問要標準（導讀）還是工具書級（窮盡）。

## 混搭指南

真實技術文常是混合體，常見配比：

- 工具教學文：概念型開場（TL;DR＋定位澄清）→ 操作型主體（可重現
  四要素）→ 概念型收尾（邊界清單＋判斷標準）
- 原理解說文：推演型主體 → 失敗模式具名化 → 操作型的「那我該做什麼」
  小節收尾
- 翻譯改寫技術文：推演型（範例先行）＋術語三層法

## 出稿前雙檢查清單

**可操作性（操作類內容逐項過）**
- [ ] 每個操作有前置條件、精確動作、預期結果、副作用善後？
- [ ] 操作以意圖為索引（if 想達成 X → how）而非功能表順序？
- [ ] 指令可複製、附 why 註解？
- [ ] 有「什麼時候不適用」清單與一條可自行套用的判斷標準？
- [ ] 讀者做完每步能自我驗證（預期結果寫了嗎）？
- [ ] 版本／環境差異有標注？不確定的標「理論上」「據我測試」？

**概念釐清（概念類內容逐項過）**
- [ ] 概念以「它決定了什麼行為」陳述，而非抽象定義？
- [ ] 與讀者腦中最近的混淆對象做了切割對比？
- [ ] 承重概念有立樁並反覆回扣？
- [ ] 難概念有白話翻譯或比喻回收？
- [ ] 機制講了 why（讀者能推理未涵蓋情況）？
- [ ] 誠實寫了缺點與邊界？
