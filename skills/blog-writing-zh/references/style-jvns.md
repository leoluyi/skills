# Julia Evans（jvns.ca）— 賦能解惑型【概念釐清標竿】

**定位**：替「用了多年還是害怕自己工具」的工程師卸除恐懼。核心信念：
"I think it sucks to be afraid of the tools that you use in your work
every day!" 適用：概念解惑、除錯思維、工具深入理解。

## 核心方法

**1. 承認困惑當教學法。**
從「我用 git 十年了，早就忘記它哪裡難」出發，刻意重建初學者視角
（她為 git zine 找了 66 位 beta readers 專門找出「我以為講清楚了
其實很混亂」的頁面）。寫作姿態永遠是 "I was super confused by this
thing just recently, let me explain it!!"——不是專家俯視，是剛爬出
坑的人回頭拉一把。

**2. 困惑源具名化。**
不說「git 很難」，而是點名困惑的具體類型：confusing terminology
（fast-forward、remote-tracking branch）、misleading messages
（"Your branch is up to date" 其實不一定 up to date）、
uninformative output。命名之後，讀者的挫折感從「我很笨」轉成
「這工具的介面確實有問題」——羞恥感卸除是她的教學前提。

**3. 可觀察行為優先於內部原理。**
解釋策略是「把你在 UI 看到的現象，接到底下的邏輯」，而不是從
內部架構教起。讀者已經天天看到那些錯誤訊息——從現象出發，
理解立刻有掛勾。

**4. 恐懼日常化示範。**
展示專家處理「可怕訊息」的實際日常：「看到 failed to push some
refs，想『喔對，同事大概推了新 commit』，跑 git pull --rebase，
繼續過我的日子。整件事十秒鐘。」把讀者最怕的場景演成十秒鐘的
例行公事，恐懼自然消解。

**5. 批評與愛並存＋個人實踐揭露。**
「這篇把 git 講得很糟，但我只為我愛的技術寫 zine」；誠實標注
危險區並揭露自己的作法（「stash 是最容易搞丟工作的地方之一，
所以我自己很少用」）。個人取捨的揭露比中立建議更有用。

**6. 探索實況文體。**
許多文章「問題比答案多」，是對主題的 live 探索而非講解
（Dan Luu 評語）。相關文體：TIL、"WHY DID NOBODY TELL ME ABOUT
THIS BEFORE?!" 型小工具驚喜文、輪詢讀者困惑再回應的 poll 文。

## 進階招式

此風味橫跨兩種子模式，下筆前先定位在哪一端：

**內部光譜：打磨解惑 ↔ live 探索。**
- 打磨解惑型：主題她已精通，目標是替讀者卸除恐懼。用「困惑源
  具名化＋恐懼日常化」（DNS 的 negative caching 花了她五年才懂，
  懂了以後反應是「什麼，就這樣？我覺得有點被騙了！」）。
- live 探索型（TIL/日誌）：主題她也剛在學，公開未完成的探索
  （「也許明天我就能真的搞懂 gzip 怎麼用 Huffman coding」）。
  問題比答案多，展示過程不假裝結論。
選題後定位：教你已懂的→打磨解惑；記你在學的→誠實 live 探索。

**招式：**
1. **「花了 N 年」誠實時間帳**：揭露某個小知識實際花多久才懂
   （「花了五年才意識到」），把難度歸於知識本身難得而非讀者笨。
2. **反爬升金句**：學會後回望的釋然——「我覺得有點被騙了，
   這根本不難」——精準命中卡關者的心理。
3. **同儕見證**：「我問過很多很厲害的工程師朋友，他們也…」——
   用他人也困惑證明這不是讀者的問題。
4. **權威指路不搶功**：主題已有好資源就直接推薦（「想真的懂
   就去讀那一頁」），不硬把別人的內容重寫一遍。

## 標題公式

- 直白現象型：「SQL queries don't start with SELECT」——標題本身
  就是一個顛覆認知的事實陳述
- 誠實問句型：「Why is DNS still hard to learn?」「git rebase:
  what can go wrong?」
- 謙抑筆記型：「Some notes on X」「Some miscellaneous git facts」
  ——降低承諾、降低讀者戒心

## 與中文來源的對應

高見龍概念型＋倉鼠推演型的極致版，外加獨有的「情緒工程」層：
先處理讀者的羞恥與恐懼，再處理知識。中文技術寫作極少做這層。

## 禁忌

- 不裝全知：不確定就寫「I'm not sure」；她的信任來自誠實不來自權威。
- 不嘲笑困惑：讀者的每個困惑都被當成工具設計的線索，不是讀者的錯。
