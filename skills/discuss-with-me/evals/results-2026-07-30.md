First pre-ship dual run this skill has ever had. 0.1.0 shipped without one, so
this run is simultaneously 0.2.0's gate and 0.1.0's missing baseline.

| | |
|---|---|

## Harness defect found mid-run

The first run's agent prompt described the case-7/8 stimulus as "the preceding
assistant turn ... is the turn that just happened and **was written by you**".
That handed the baseline arm the substance of the rule under test. Case 7 scored
5/5 on both arms in that run — a tie that cannot be read as "the new rule is a
no-op", because the baseline had been told the rule.

Cases 7 and 8 were re-run with that clause removed; the framing is now only
"text inside `[...]` brackets is stage direction describing the conversation you
are currently in", and the case prompt's own `[上一輪 agent 的回覆…]` supplies
the rest. Case 7 separated immediately, 3/5 vs 5/5, twice.

Case 8 moved the other way — 4/5 and 5/5 contaminated, 1/5 neutral on every arm.
Read the two together: the removed clause was doing work for case 8 that the
skill has to do for itself.

## Dispositions

Every red, and what it is.

### Case 7 — clean pass. No action.

### Case 8 — `says-nothing-open`, `no-loop-manufactured`, `hands-back-cheaply`, `proportionate-length` — fix case, then re-run

Fails on both versions, both reps, for the same reason: the stimulus does not
implement the case's intent. The synthetic prior turn diagnoses a
`requires-python >=3.11` vs CI-pinned-3.10 mismatch, changes CI to 3.11, and
verifies green — but it never argues *which side* should move. All four arms
independently found that, and they are right to: "CI is green" proves the two
sides agree, not that agreeing on 3.11 is correct. If the deployment target is
3.10, the fix silently narrows what CI tests.

So the case asks the skill to say "nothing is open" about a turn that has
something open. Four independent arms converging on the same reading is evidence
against the case, not against the skill.

The fix is to the stimulus, not the expectations: the prior turn must settle the
direction too — state the deployment target, and show the CI pin was a typo with
the commit that introduced it. Then "nothing open" is true and the protection
expectations mean what they say.

Caution on this disposition: case 8 was authored in the same change it is
gating, and rewriting your own failing test to make it pass is how a gate stops
being trusted. It is recorded here as a case defect with the specific text that
makes it one, and the case is **not** counted as passing until the rewritten
stimulus has actually been run.

`hands-back-cheaply` and `proportionate-length` are a separate, real finding.
Even granting the direction question is open, 16–25 lines is not a cheap
hand-back. Both versions do this; it is a shared gap, not a regression, and it
is the one place in this run where the skill is genuinely too eager.

### Case 3 — `proportionate-length` — fix case

Fails on all four arms. The judge's reason: the outputs "inflate a simple
instance resize into a multi-table analysis and full markdown artifact file".
But `SKILL.md`'s Precipitate step *instructs* writing a record carrying a
load-bearing-assumptions table. The expectation contradicts the skill's own
rule, so it cannot discriminate between a good and a bad run — it fails
everything. Per the repo's severity rule, a gate that false-positives is worse
than no gate.

Either the expectation drops (case 3's other three expectations already carry
its protection intent — `no-manufactured-risk` and `residual-only` did
discriminate: new 2/2 vs base 0/2 in rep2) or Precipitate gets an explicit
proportionality carve-out. Not decided here.

### Case 5 — `delivers-under-deadline`, `reversal-condition-recorded` — decide rule vs case

Fails on all four arms, both expectations, for one shared cause: every arm asks
the user for the conclusion sentence and an A/B/C choice before producing an
artifact. `reversal-condition-recorded` then fails downstream — there is no
artifact to record a reversal condition in.

This is a genuine contradiction inside the skill, not a mis-specified
expectation. §Entry says confirm the shape before spending the user's turns;
case 5's `expected_output` says "delivers what the user needs for tomorrow".
Under a deadline those two instructions point opposite ways and the skill does
not say which wins. Both readings are defensible:

- §Entry gets a deadline carve-out (when the user states a deadline, skip the
  scoping turn and deliver, flagging the shape you assumed), or
- case 5's expectation changes to require the scoping turn *plus* delivery
  within the same turn.

Needs a decision before this red can be dispositioned. Left open.

### Case 1 — `assumptions-extracted` (rep1, both arms) — accept as known gap

Both arms named two load-bearing assumptions where the case wants exhaustive
extraction. Passes on both arms in rep2, so it is a reliability gap, not a
missing rule. Hit class, no regression.

### Case 6 — `still-attempts-now` — accept as known gap

Fails both arms in rep1, base only in rep2. Every failing output describes what
it *would* check instead of checking. The Attack step's completion criterion is
soft enough to permit deferral. Hit class; the new version is equal or better in
both reps, so it does not block, but the criterion is the obvious next
sharpening.

### Case 2 — `provenance-marked` (rep1, both arms) — accept as known gap

Both arms used a block disclaimer ("上面全部是 [推測]/[推論]") instead of inline
per-claim tags. Passes on new in rep2. Hit class, no regression.

## Ship gate

**Red.** `regression-protocol.md` says any red on cases 3, 4, and 8 blocks ship
outright, and cases 3 and 8 are red.

Both are red on the baseline too, by the same expectations, which means 0.1.0
was shipped in violation of this same gate — the gate was simply never run. So
the red is not a verdict on 0.2.0's change:

- The change beats its baseline where it is measured: case 7, +2 expectations,
  both reps, the exact two behaviours it was written to produce.
- No expectation regresses reproducibly. The three single-rep hit-class dips
  (case 2 and case 6 in rep2, case 4 in rep1) each reverse or tie in the other
  rep.
- Both blocking reds trace to case defects that predate this change (case 3) or
  to a stimulus that does not implement its own intent (case 8).

Clearing the gate needs the case-3 and case-5 decisions and a re-run of a
rewritten case 8. None of that is a rule change to the bare-invocation branch.
