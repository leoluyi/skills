# 維護這個 skill

**改這個 skill 之前先讀這裡。**

它是一套**推導系統**：正確性不在文字寫得多好，而在數值能不能重算出來、
規則能不能被腳本擋下。改它時最容易犯的錯不是改錯值，
是**把推導出來的東西寫成常數**。

## 五條紀律

### 1. 值用算的，不用寫的

任何可以從別的值推導出來的東西，都不該手寫第二份。
手寫的那份不會跟著公式更新，而且沒有測試會抓到。

已經發生過：三個 `pens/*.md` 各手寫了一張虛線陣列表（`6 4`、`8 5`、`10 7`），
那是 `dashes(sw)` 的輸出。改係數就會不一致。

**判斷法**：如果改了 A 之後 B 也得跟著改，B 就不該存在。

### 2. 規則要有閘門，否則會漂

寫在文件裡的規則等於沒有規則——三個月後沒人記得。
每加一條規則，同時問：`derive.py` 或 `check_fit.py` 能不能擋下違反它的情況？

不能擋的規則有兩種下場：被忘記，或被違反而沒人發現。
`category lightness` 那條就是折衷——並列類別合法地不遞增，
所以它回報而不擋，但至少會出現在輸出裡。

### 3. 量，不要看

顏色的錯誤在彩色螢幕上看起來完全正常。
Bootstrap 的 primary 與 success 明度**完全相同**，眼睛看是藍與綠，
影印出來是同一塊灰。

每個門檻都要有推導或實測依據，寫進 `constants.md`。
**「大概這樣」的數字最後都會被發現是錯的**——`MAX_CATS=4` 曾經宣稱
「淡底可用明度約 42 點」，實測是 60 點，那個上限根本不存在。

### 4. 改完跑回歸

```bash
python scripts/test_themes.py          # 19 個基準
python scripts/render_reference.py     # 重生參考頁
```

這條不是形式。修 A 引出 B 的情況在這個系統裡發生過至少四次，
清單在 `regressions.md`。

基準有差異時**先看 diff 再 `--update`**。差異是預期的才重建。

### 5. 層與層之間不要互相下放

角色是契約，筆調與顏色是實作。`state/planned` 是角色，
它的虛線長度隨筆調縮放——但那不表示狀態屬於筆調。

曾經把狀態巢狀在筆調底下呈現，等於宣稱狀態歸筆調所有。
**view 可以反正規化，source 不行。**

## 改一件事的流程

1. **先找常數登記表**（`constants.md`）——那個數字可能有推導，
   改它會牽動別的。
2. **確認要改的是哪一層**——值？公式？門檻？規則？四者的影響範圍差很多。
3. **改**，同時更新它的推導說明。沒有推導的數字不要留。
4. **跑回歸**，看 diff。
5. **重生參考頁**，按灰階檢視看一次。
6. 若加了新規則，回頭補一個 `tests/cases.json` 案例。

## 常見的改動

| 使用者要什麼 | 讀哪份 |
|---|---|
| 加一組色票 | `../references/adding-a-theme.md` |
| 調推導階梯或門檻 | `constants.md` |
| 加新角色（節點型別、狀態、線型） | `../references/roles.md` 的通道分配 |
| 加筆調選項 | **先確認那不是形狀**——形狀承載意義，屬角色 |
| 重構參考檔 | 檔名要能還原心智模型：角色 → 三層 → 媒材 |
