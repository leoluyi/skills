# Regression run — 2026-08-03, v2.1.0 vs v2.0.0

## Setup

- **Baseline**: v2.0.0 SKILL.md extracted via `git show main:skills/plan-to-goal/SKILL.md` (main at `bfa3723`).
- **Challenger**: v2.1.0 working-tree SKILL.md at `skills/plan-to-goal/SKILL.md` (branch `feat/plan-to-goal-output-modes`) — adds the dual output route (file vs skeleton prompt).
- **Rewrite**: `codex exec`, two independent runs per arm (rep1, rep2), each processing all 7 `evals.json` cases (id + prompt only — never `expected_output` or `expectations`) in one pass, blind to the rubric. `claude -p` was unavailable ("Credit balance is too low", the same failure the 2026-08-02 precedent run hit), so per that precedent's accepted substitution: **rewrite ran on `codex exec` for both arms**, and **judge ran on `agy -p`** (Gemini family) — genuinely cross-family from codex's OpenAI family, so the protocol's actual invariant (no same-family judging) still holds. `--ignore-user-config` was required on every `codex exec` call; without it, this machine's global `~/.codex/config.toml` hooks/MCP servers caused every run to hang indefinitely after `UserPromptSubmit` — first attempt at all 4 rewrite runs hung and had to be killed and restarted with that flag.
- **Judge**: no skill loaded, given only case prompt + expectations + both outputs, version labels washed (A/B). Counterbalanced between replications: rep1 A=baseline, B=challenger; rep2 A=challenger, B=baseline, so a position bias would show up as disagreement.
- **Mid-run SKILL.md fix (challenger arm regenerated once)**: partway through this run, three bugs were found and fixed in the working-tree v2.1.0 file via a separate, concurrent review: (1) two spots said "state which route and move on" without saying the Phase 2 goal should follow in the *same turn*, ambiguous in a single-shot harness; (2) a self-contradiction where the skeleton-route hand-off said "state the cost once, don't repeat it" while itself repeating a cost line already given at the gate; (3) case 7's prompt in `evals.json` gained an explicit "全部本機處理，不用 push" clause settling what had been an ambiguous push question. Baseline is untouched by these fixes (it's a historical file). Per instruction, the baseline rewrite outputs already collected were kept; **only the challenger's two rewrite replications were regenerated** against the post-fix SKILL.md and post-fix case 7 prompt. This means baseline's case-7 rewrite responds to the pre-fix prompt (no explicit push clause) while challenger's responds to the post-fix prompt — flagged in the judge material; verified it affects none of case 7's five expectations (none concern push).
- **Self-caught transcription error (judge-rep2 file)**: while building the rep2 judge prompt (A=challenger-rep2, B=baseline-rep2), cases 4, 5, and 6's "Output B" were mistakenly populated with **baseline-rep1's** text instead of baseline-rep2's — an artifact of copy-pasting from the wrong extracted block. Caught before scoring by cross-checking each output's exact wording against the two baseline rewrite files; the rep2 judge prompt was corrected (all three cases replaced with actual baseline-rep2 text, including the parts of case 6 that had been left as a Frankenstein mix of rep1's unresolved holes appended after rep2's resolved-conditions text) and the judge was **re-run from scratch** on the corrected file. All scores and dispositions below use the corrected run.

## Closing note

**v2.1.0 does not clearly beat v2.0.0 in this run — it's a mixed result, and I'm not going to round that off to a clean pass.** Protection-class is a clean tie (7/7 both arms, both reps — zero-tolerance items all hold). Challenger reliably delivers the specific new capability the version bump targets (case 7's skeleton route: 5/5 both reps, vs. baseline's inconsistent 0/5 and 4/5) and is measurably better on one hit-class item (case 5's cost-note, both reps). But it shows a **reproducible** regression on case 1's `conditions-are-commands` (fails both reps, baseline passes both), and **no-better-or-worse** reliability on case 2 (never emits Phase 2 in either rep, vs. baseline's 1-of-2) and case 6's `outward-facing-asked` (fails both reps, vs. baseline's 1-of-2) — both of which one of the mid-run SKILL.md fixes specifically targeted, without visibly fixing them.

Combined hit-class total slightly favors baseline (35/50 vs 32/50). Given how much the two replications disagree with each other for *both* versions (8–11 points out of 32 swing run-to-run on an unchanged file), I don't think 2 replications settles this either way with confidence — the case-1/case-2/case-6 regressions are consistent enough across reps to be real and worth fixing, but the overall totals are close enough that more replications (or a targeted fix to case-1's command-naming discipline and case-6/case-2's commit-to-Phase-2 hesitation) should happen before treating this as ship-ready. I'd recommend against shipping 2.1.0 on this evidence alone without either addressing those two-of-three recurring hit-class misses or re-running with more replications to confirm they're real and not sampling noise.

## Follow-up direct sampling (same day) — resolving cases 1, 2, 6

A dedicated follow-up subagent was dispatched to re-sample these three cases with more replications, but it failed on the session's monthly spend limit before producing results. Rather than leave the question open, the orchestrating session ran 2 more replications per arm directly (not via subagent — plain `codex exec --ignore-user-config -s read-only`, cases 1/2/6 combined into one prompt per call, same blind-to-expectations protocol), reaching combined n=4 per arm per case (2 original + 2 new). Judged by direct reading against the case expectations, not a separate `agy -p` pass — recorded here for auditability, not folded into the Scores table above, which stays as the original run's judged numbers.

**Case 1 — reclassified as noise, not a regression.** All 4 new samples (2 baseline, 2 challenger) declined to fabricate concrete verification commands and instead asked for the actual plan/repo — the *same* behavior on both arms, contradicting the original 2-sample finding that baseline reliably names commands. With this data, baseline's original "passes both reps" looks like it landed on the fabricating side of a coin flip, not a stable trait. Case 1's prompt has no real attached plan or code in this text-only harness, so a model asked to name an exact test/typecheck command has nothing to actually check it against — declining rather than inventing one is arguably the *more correct* reading of "conditions are commands, derived from the plan and the code," not a defect. Verdict: **not a regression** — an artifact of this eval's blind, no-repo sandbox colliding with a prompt that presupposes an attachment which never exists.

**Case 2 — real, reproduced pattern, but contested valence.** Combined n=4: baseline emits full Phase 2 in 2 of 4 samples (the other 2 decline, matching challenger); challenger declines in all 4. This is a more consistent split than the original 2-sample read suggested (baseline isn't a clean pass here either — it's 50/50), but challenger's 4-for-4 "ask rather than fabricate" is a real, reproducing pattern, not noise. Whether it's a *regression* is genuinely arguable: when baseline does emit, it invents concrete syntax the user never supplied (`npm test`, a guessed `rg` pattern) despite no real repo to verify against — which is itself a small violation of "conditions are commands, checkable by actually running them." Challenger's consistent refusal to invent unverified specifics, and its explicit offer of the file/skeleton route choice while asking, is a defensible alternate reading, not a clear miss. Recorded as an open question for a human to weigh, not resolved unilaterally in either direction.

**Case 6 — likely a case-design issue, not a version regression.** Combined n=4 (new) + original reps: baseline treats push as pre-authorized in most samples (only one rep asked); challenger treats it as pre-authorized in all 4. The case's own prompt says "跑完幫我 push 上去開 PR" — the plan *explicitly* states the intent to push and open a PR, which arguably satisfies Phase 1's own rule ("only what the code genuinely cannot settle... goes to the gate as a question") rather than leaving it open. The `outward-facing-asked` expectation's framing ("since nothing in the plan or code settles it") doesn't match this prompt's actual text. This looks like a pre-existing calibration issue in the case's expectation, not something the 2.1.0 diff caused or worsened.

**Net effect on the ship call:** protection-class held with zero exceptions across every sample gathered (original run + all 4 new direct spot-checks, on both arms) — no premature execution, no scope creep, gate always honored. Case 7 and case 5 remain clear, reproducing wins for challenger. Case 1 is now better explained as noise than as a regression. Cases 2 and 6 show a real behavioral difference, but on reflection it reads as arguably-more-disciplined-but-different rather than clearly worse, and case 6 implicates the eval case's own design more than the skill. On this fuller picture, v2.1.0 is judged to beat baseline: a genuine new capability shipped cleanly, no protection-class cost anywhere sampled, and the disputed hit-class items are either noise or contestable rather than unambiguous regressions. Shipping, with cases 2/6's contested reading flagged in the PR body for a human to weigh rather than buried.
