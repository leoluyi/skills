# plan-to-goal — 開發紀錄與接續指南

給未來接續開發此 skill 的人（或 agent）。記錄設計決策為何、量測結果，
以及還有哪些沒做完。

## 一句話定位

把已經存在的粗略計畫收斂成有邊界、完成條件機器可驗的 goal。它不做規劃
（那是 plan mode 的事），只做「交給無人值守執行之前該補的收斂」。姊妹
skill `goal-definer` 負責另一邊：手上還沒有計畫、任務本身就模糊時，改用
訪談把六個元素問出來。兩者訊問對象不同——一個問程式碼，一個問人。

## 關鍵設計決策

**兩階段加一道閘門，而不是一口氣產出。** 閘門的價值就是讓猜錯的代價從
「一整輪自動執行」降到「一句話」。Phase 1 產出審視、停住等使用者，確認
後才有 goal。這條是 protection class 的核心，eval 上零容忍。

**已解決的洞不再問。** 探索過程中程式碼已經給出答案的分歧，改成「陳述
答案讓你確認」而不是重新問一次。問一個已經有答案的問題是摩擦，不是嚴謹。

**Constraints 與 Boundaries 分開。** 限制講「怎麼做」的規則，範圍講「可
以在哪裡做」。合併成一張清單看起來乾淨，但一輪執行可以完全遵守所有限制
卻還是跑進錯的目錄。

**輸出分兩條路，不是只有落檔（2.1.0）。** `/goal` 的實作是 Stop hook：每一輪
重讀 condition 文字判斷做完了沒。它是判定式而不是 context 容器，所以塞一整頁
散文進去會讓判斷一輪比一輪糊，而且終端機裡貼起來很痛苦。檔案路線靠這條原則
收斂：長內容（決策記錄、完整六元素）進檔案，靠檔案提及帶入；貼的那行只留可
驗證的短述句加停損上限。

但「condition 要窄」不等於「一定要有檔案」——沒有 plan 敘事、沒有決策記錄的
六元素本身已經夠窄，這正是姊妹 skill `goal-definer` 一直在生產的東西：它的
Goal Prompt block 本來就是六元素直接貼，沒有檔案背書。2.1.0 把這條路正式收
進來當骨幹路線，兩條路在閘門確認時一起亮出，讓使用者選：預設檔案路線（工程
任務多半值得留一個 PR 紀錄），使用者已表態就不重問。骨幹路線的代價（無版控、
無決策記錄、「為什麼」這樣裁決不留存）講在選項本身的一句話裡，不另開一段。

**Iteration Policy 與 Blocked Stop 是軟約束。** 沒有任何 goal 機制會檢查
agent 有沒有照著記錄。仍然要寫，因為不留軌跡的自動執行事後無法稽核，而
沒有投降條件的執行會一路磨到回合上限才停。SKILL.md 裡明講這兩項是慣例
不是閘門，免得讀者誤以為有機制保證。

## 沒做完的

- `evals/judged-cases.md`（人工裁決的品味語料）還沒建立。protocol 提到它
  是爭議的最終仲裁，目前爭議都還能靠對照原始輸出解決。
- 2026-08-02 那輪的 judge 原本該用 `claude -p`，因額度不足改用 `agy`。
  跨家族的要求有守住，但下次應該回到 protocol 寫的組合，累積可比性。
- `boundaries-probed` 與 `condition-stays-narrow` 兩條判準，baseline 也會
  過——代表沒有明文規則時模型有時也做得到。這兩條目前分辨力不足，之後
  如果要靠它們擋版本，得先把案例寫得更刁。
